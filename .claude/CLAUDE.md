# CLAUDE.md

Проект: **git-rewind-mcp** — MCP-сервер для навигации по истории git и ответов на вопросы
«как это появилось / когда добавлено / для чего нужно».

## Спека: .claude/SPEC.md

[.claude/SPEC.md](./SPEC.md) — источник правды по замыслу и текущему состоянию проекта.
Код отвечает на вопрос «как сделано», SPEC.md — на «что делаем и что уже сделано».

### Когда читать

- **В начале каждой сессии** — до того, как что-то планировать или писать.
- **Перед реализацией любой задачи** — свериться, входит ли она в текущий этап,
  нет ли по ней уже решения в разделе «Решения» или открытого вопроса.
- **Когда задача звучит противоречиво** — сначала смотреть SPEC.md, потом спрашивать.

Если задача расходится со спекой — не молчать и не подгонять: сказать об этом
и уточнить, меняем ли спеку.

### Куда что записывать

SPEC.md состоит из фиксированных разделов:

| Раздел | Что туда идёт |
|---|---|
| Назначение, Формы входа | Замысел продукта. Меняется редко и осознанно. |
| Этапы | Крупные фазы (что делаем сейчас, что отложено). |
| **Реализовано** | То, что уже работает и проверено. Одна строка — одна возможность. |
| **В работе** | То, что делается прямо сейчас. Держать коротким: 1–3 пункта. |
| **Дальше** | Что запланировано, но ещё не начато. |
| Решения | Выбранное и зафиксированное (стек, транспорт, форматы) — с причиной. |
| Открытые вопросы | То, что ещё не решено. Решили — переносим в «Решения» и убираем отсюда. |

### Когда обновлять

- **Взялся за задачу** → перенести пункт из «Дальше» в «В работе».
- **Закончил и проверил** → перенести из «В работе» в «Реализовано».
- **Принял решение по открытому вопросу** → перенести его в «Решения» с причиной.
- **Появилась новая идея/задача** → добавить в «Дальше», не начиная делать.

Обновление спеки идёт **тем же коммитом**, что и сам код. Не откладывать «на потом»:
спека, которая отстаёт от кода, хуже отсутствующей.

### Чего в SPEC.md быть не должно

- Пересказ кода: сигнатуры, структура файлов, детали реализации.
- История изменений и changelog — для этого есть git.
- Задачи «на подумать» без привязки к разделу.

Формулировки — короткие и проверяемые: «инструмент возвращает историю файла с диффами»,
а не «улучшена работа с историей».

## Как работать над проектом

- Этап 1 — только `git log` / поиск по истории / diff. Векторную БД и RAG сейчас не трогаем,
  даже если задача выглядит как повод их прикрутить.
- Ответы инструментов всегда содержат конкретные коммиты (sha, автор, дата, сообщение) —
  агент не должен додумывать источник.
- Открытые вопросы из SPEC.md не закрывать в одиночку: спросить и зафиксировать ответ.
