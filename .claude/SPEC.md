# SPEC — git-rewind-mcp

Живой документ. Описывает **что** делает проект и **в каком состоянии** каждая часть.
Правила ведения — в [CLAUDE.md](./CLAUDE.md).

## 1. Назначение

MCP-сервер, который помогает ходить по коммитам и отвечать на вопросы об истории кода:

- «Как это появилось?»
- «Когда это было добавлено?»
- «Для чего это нужно?»

Пользователь спрашивает через агента (Claude Code и другие MCP-клиенты), сервер ищет ответ
в истории git и возвращает коммиты + diff, на которые опирается ответ.

## 2. Формы входа

Вопрос может прийти в трёх формах — все три сервер должен понимать:

| Форма | Пример | Что делает сервер |
|---|---|---|
| Свободный вопрос | «когда мы перешли на pnpm?» | ищет по сообщениям коммитов и содержимому диффов |
| Выделенный участок файла | фрагмент кода + путь | история именно этих строк (`git log -L`), кто и когда их ввёл |
| Указание на файл | `src/server.ts` | история файла целиком, включая переименования |

Ответ всегда со ссылками на конкретные коммиты (sha, автор, дата, сообщение) и релевантный diff —
агент не должен догадываться, откуда взялся вывод.

## 3. Этапы

### Этап 1 — поиск по git (текущий)

Только `git log` / поиск по истории / diff. Без индексов и внешних зависимостей.

Опора: `git log -S` и `-G` (поиск по содержимому изменений), `git log -L` (история диапазона строк),
`--follow` (переименования), `git show` (diff коммита), `git blame` (кто ввёл строку последним).

### Этап 2 — векторная БД + RAG (отложено, не делаем сейчас)

File-based векторное хранилище рядом с репозиторием + RAG поверх истории коммитов,
чтобы отвечать на смысловые вопросы («для чего нужно?»), а не только на текстовое совпадение.
Подключается, когда Этап 1 работает и понятно, чего ему не хватает.

## 5. Решения

Зафиксировано и не пересматривается без причины.

- **TypeScript + официальный MCP SDK v2** (`@modelcontextprotocol/server`), рантайм Node.js 20+.
  Взяли вторую версию, а не зрелую `@modelcontextprotocol/sdk` 1.x: проект новый, тянуть старое
  API незачем, API v2 заметно короче. Сервер раздаётся через `npx` без сборки у пользователя.
- **Имя пакета — `@ruslan-aktaev/git-rewind-mcp`**, скоуп совпадает с ником в npm.
  Публикация публичная: в `package.json` нужен `publishConfig.access: "public"`,
  иначе npm попытается опубликовать скоупный пакет как приватный.
- **Транспорт — stdio.** Сервер запускается клиентом как локальный процесс (`npx`)
  и общается по stdin/stdout. Сетевой транспорт не нужен: сервер читает локальный клон.
- **Доступ к git — вызовы `git` CLI**, не библиотека. Проект стоит на `log -S/-G`, `log -L`
  и `--follow`; в библиотеках это либо отсутствует, либо пришлось бы реализовывать вручную.
- **Только чтение.** Сервер не меняет рабочее дерево, индекс и историю. Мутирующих
  инструментов (revert, восстановление файлов) нет и на этапе 1 не планируется.
- **Целевой репозиторий — рабочая директория клиента по умолчанию**, плюс необязательный
  параметр пути у инструментов. Работает без конфигурации, но переживает монорепы
  и несколько репозиториев в одной сессии.

## 6. Ограничения

Осознанно принятые границы этапа 1. Для MVP и MLP истории git достаточно — эти пункты
не блокируют выпуск. Возможно, снимем их позже, но отдельным решением, а не по ходу дела.

- **В git нет обсуждений.** Описания PR, комментарии ревью и issues лежат в GitHub,
  а не в репозитории. На вопрос «для чего нужно?» из истории достаём максимум номер PR
  из merge-коммита. Снимается интеграцией с GitHub API — не сейчас.
- **Shallow-клон** (`--depth 1`, обычное дело в CI) истории просто не содержит.
  Сервер должен это распознавать и честно говорить пользователю, а не отдавать пустой
  результат как отсутствие изменений.
- **Репозиторий должен быть склонирован локально.** Сервер не ходит в сеть и не клонирует
  сам — работает только с тем, что уже есть на диске.
