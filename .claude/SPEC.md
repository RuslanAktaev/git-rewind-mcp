# SPEC — git-rewind-mcp

Живой документ. Описывает **что** делает проект и **в каком состоянии** каждая часть.
Правила ведения — в [CLAUDE.md](./CLAUDE.md).

## 1. Назначение

MCP-сервер, который отвечает на вопрос «делали мы уже такое где-нибудь?».

Разработчик берётся за задачу и хочет знать, решалась ли она в компании раньше: в этом
проекте, в соседнем, три года назад. Сервер ищет по merge request'ам всех проектов GitLab,
где состоит пользователь, и возвращает конкретные MR со ссылками.

Пользователь спрашивает через агента (Claude Code и другие MCP-клиенты). Агент читает
найденные заголовки и решает, то это или мимо, — сервер вердикта не выносит.

## 2. Форма входа

Свободный вопрос: «делали мы двухфакторную авторизацию?», «где-нибудь настраивали
экспорт в pdf?». Ответ — до пяти merge request'ов: проект, номер, дата, заголовок, ссылка.
Diff не храним: он есть в GitLab и достаётся по номеру MR, когда понадобился.

Запрос к поиску формулируется по-английски — база английская целиком, см. «Решения».

## 3. Чего сервер не делает

**Историю git одного репозитория — не трогаем.** Это был первый этап, он написан
и удалён (`file_history` и `health` живут в коммите `a308772`). Причина: агент с доступом
к шеллу делает то же самое сам, без всякого сервера, и заставить его пользоваться
инструментом невозможно — проверено на живом Claude Code.

Осознанная жертва: у клиентов **без шелла** (Claude Desktop, часть IDE-плагинов) такой
альтернативы нет. Если они окажутся важны, код достаётся из истории.

Оставшийся смысл проекта — ровно то, чего агент с шеллом не может никак: поиск по 22 365
merge request'ам 106 проектов, до которых с локальной машины не дотянуться.

## 4. Состояние

### Реализовано

- Скелет сервера: сборка TS, bin-энтрипоинт для `npx`, подключение по stdio, `tools/list`.
  Инструментов пока ни одного: git-инструменты удалены, поисковый ещё не написан.
- Команда `index`: выкачивает merge request'ы всех проектов, считает векторы и кладёт
  их вместе с полнотекстовым индексом в один файл SQLite. Полный прогон — 22 366 MR
  из 106 проектов, 99 МБ. Повторный запуск дотягивает только изменившееся.
- Внятные отказы вместо стека: нет хоста, нет токена, не отвечает ollama, старый Node,
  индекс построен другой моделью.
- Инструмент `search_mrs`: по английской фразе отдаёт до 20 merge request'ов с проектом,
  номером, датой, ссылкой и близостью. Ниже порога 0.675 списка не отдаёт вовсе — говорит,
  что такого не делали. Рядом печатает, в скольких MR встречается каждое слово запроса:
  ноль значит, что этого слова не писал никто. Русский запрос отклоняет с просьбой перевести.

### Проверено экспериментом

Замеры на полной выгрузке: 22 365 MR из 106 проектов, векторы `bge-m3`.
Скрипты и как повторить — в [spike/README.md](../spike/README.md).

- Смысловой поиск по заголовкам работает: на 13 размеченных запросах эталонный MR попал
  в пятёрку в 13 случаях из 13 (`spike/5-eval.py`).
- **Порог по оценке близости отделяет находку от промаха.** На 21 размеченном запросе
  (13 существующих тем, 8 заведомо отсутствующих) самая слабая находка дала 0.685,
  самый сильный промах — 0.667. Граница около 0.675, запас узкий (0.018), но ни одного
  пересечения. Работает при условии, что запросы английские: на русских оценка плывёт
  и порог рассыпается.
- **База целиком английская.** Кириллица нашлась в 2,3% заголовков, и та оказалась
  опечатками раскладки («сhore» с русской «с»). Русских заголовков в базе нет.
- **Русский запрос слабее английского.** `bge-m3` многоязычная, но на 22 365 записях
  «двухфакторная аутентификация» промахивается мимо настоящих 2FA (0.660, в топ-5 их нет),
  а `two-factor authentication OTP` находит с первого места (0.762). На одном проекте
  (2269 записей) разрыв был незаметен — вывод «русский работает» масштаба не пережил.
- **Отрыв от фона (в сигмах) как признак не работает — в отличие от самой оценки.**
  Проверялся как замена порогу, когда запросы предполагались русскими. Растёт с размером
  базы (находка: 4.27 на 1000 записях → 8.03 на 22 365; промах: 2.94 → 5.17), поправка
  на √(2·ln N) не спасает. И работает наоборот: несуществующий «nuclear reactor control
  panel» набирает 7.7σ на одиноком `admin panel`, а настоящий `google maps` — 5.5σ,
  потому что плотная группа настоящих совпадений сама поднимает фон. На 21 размеченном
  запросе диапазоны пересекаются и по первому результату, и по пятому.
- **Составные запросы дают ложную тревогу.** «pay with cryptocurrency bitcoin» уверенно
  находит платёжные MR: слово «pay» совпало с тысячей записей, а различающее
  «cryptocurrency» не учитывается никак. Криптоплатежей в базе нет.
- Прогон 21 размеченного запроса на TS-реализации: **21 из 21**. Все 13 существующих тем
  найдены и прошли порог, все 8 несуществующих отклонены. Числа те же, что на питоне.
- **Склейка списков по местам (RRF) проверена и отвергнута.** Записи, найденные обоими
  способами, обгоняли одинокого лидера: лучший MR с близостью 0.762 вылетал из пятёрки
  в пользу 0.682. Порядок выдачи — по близости; полнотекстовый поиск остаётся ради
  счётчиков слов и кандидатов с точным редким словом.
- Реализация на TS воспроизводит замеры спайка до третьего знака: `two-factor
  authentication OTP` даёт те же 0.762 / 0.729 / 0.724 / 0.713 / 0.690. Значит порог 0.675
  переносится на неё без пересчёта.
- Описания хуже, чем показала разведка: пустых 62% (не 40%), медиана длины 0 символов.
  Заголовок — единственный рабочий сигнал.

### Дальше

- Сделать из прогона 21 размеченного запроса команду или тест: сейчас он живёт скриптом
  вне репозитория, и перепроверить порог после правки поиска нечем.
- Ускорить повторную индексацию: сейчас она опрашивает 142 проекта по одному и тратит
  54 секунды даже когда нового нет. Глобальный `/merge_requests?scope=all&updated_after=`
  должен свести это к одному запросу.
- Инструменты поиска по MR объявляются только при наличии конфигурации (хост GitLab,
  токен, доступная ollama). Без неё сервер отдаёт одни git-инструменты.

## 5. Разведка по GitLab (21 августа 2026)

Замеры на `gitlab.example.com` через API, токен с правом `read_api`.

| | |
|---|---|
| Проектов, где состоит пользователь | 142 (36 из них без единого MR) |
| Merge requests всего | 22 365 |
| Описание пустое | 40% |
| Описание короче 40 символов | ещё 19% |
| Медиана длины описания | 16 символов |

Описания плохие, но **заголовки живые** и несут смысл: «Implemented absence period removal
for annual subscriber», «Apply booking filters to marina request». На старте этого достаточно.

Объём в токенах — около 8 млн, в контекст не влезает даже близко. Это и оправдывает
смысловой поиск: списком модели не отдать.

Векторы 22 тысяч записей займут ~140 МБ. Это один файл в памяти и поиск перебором;
векторная база окупается от сотен тысяч записей, у нас их нет.

Глобального поиска по коду на инстансе нет (Advanced Search выключен), но поиск внутри
проекта работает. Значит, точный поиск по коду делается перебором 142 запросов — без
всякой индексации.

Стоимость улучшенных описаний, если понадобится: прогнать все 22 365 MR через Haiku
(на вход diff, на выход строчка) — около 38 долларов через Batch API. Оплачивается
отдельно от подписки Claude. Пока решено не делать.

## 6. Решения

Зафиксировано и не пересматривается без причины.

- **TypeScript + официальный MCP SDK v2** (`@modelcontextprotocol/server`), рантайм Node.js 20+.
  Взяли вторую версию, а не зрелую `@modelcontextprotocol/sdk` 1.x: проект новый, тянуть старое
  API незачем, API v2 заметно короче. Сервер раздаётся через `npx` без сборки у пользователя.
- **Имя пакета — `@ruslan-aktaev/git-rewind-mcp`**, скоуп совпадает с ником в npm.
  Публикация публичная: в `package.json` нужен `publishConfig.access: "public"`,
  иначе npm попытается опубликовать скоупный пакет как приватный.
- **Транспорт — stdio.** Сервер запускается клиентом как локальный процесс (`npx`)
  и общается по stdin/stdout. Сетевой транспорт не нужен: сервер читает локальный клон.
- **Истории git одного репозитория в сервере нет.** Агент с шеллом делает это сам —
  проверено: при подключённом сервере и видимом инструменте модель всё равно шла в Bash.
  Инструмент выгоднее шелла сделать не удалось, а клиентами без шелла решено пожертвовать.
- **Только чтение.** Сервер не меняет рабочее дерево, индекс и историю. Мутирующих
  инструментов (revert, восстановление файлов) нет и на этапе 1 не планируется.
- **Эмбеддинги — локально через ollama**, модель `bge-m3` (1,16 ГБ, 1024 измерения).
  Взяли многоязычную вместо `nomic-embed-text` (274 МБ, 768 измерений): та понимала только
  английский и на русский запрос выдавала мусор. Цена решения — вчетверо больший вес модели
  и на треть медленнее счёт (2269 записей за 40 секунд против 28 на M1 Pro); взамен вопрос
  можно задавать на языке, на котором он возник. Модель задаётся переменной `EMBED_MODEL`.
  У Anthropic эмбеддингов нет — Claude API умеет только генерацию, так что за ними всё
  равно идти в другое место.
- **Драйвер SQLite — встроенный `node:sqlite`, требование Node 22.13+.** Замер на наших
  22 365 записях: поиск 16,6 мс против 16,8 у `better-sqlite3`, файл одинаковый, заливка
  вдвое дольше (3,7 с против 1,6) — но это разовая операция. Решило другое: `better-sqlite3`
  нативный, его бинарник должен совпасть и с платформой, и с версией Node, иначе установка
  через `npx` уходит в компиляцию. Встроенный модуль перестал требовать флаг
  `--experimental-sqlite` с Node 22.13, с 25.7 у него статус release candidate.
  Цена — предупреждение `ExperimentalWarning` в stderr при старте.
- **Хранилище векторов — sqlite-vec.** Один файл, без докера и сервера, полнотекстовый
  поиск SQLite рядом даёт гибридный поиск бесплатно. Vectra отвергнута как нишевая
  (32 тыс. загрузок в неделю против 1,4 млн), pgvector — как избыточная.
- **Запросы к смысловому поиску — на английском.** База английская целиком, и русский
  запрос на ней промахивается. Перевод бесплатный: его делает сам агент по дороге, отдельная
  модель не нужна. Закрепляется двумя способами — требование в описании параметра плюс
  проверка на сервере, которая отвечает «переформулируйте по-английски» вместо поиска.
- **Отсечка по оценке близости, последнее слово за агентом.** Ниже 0.675 сервер говорит
  «похожего не нашлось» и не отдаёт список — на 21 размеченном запросе порог не ошибся.
  Выше — отдаёт пятёрку заголовков с оценками, но вердикта не выносит: запас у порога
  всего 0.018, а агент видит то, чего не видит число (что `admin panel` — не про реактор).
- **Сервер не делает предположений о среде.** Адрес ollama, хост GitLab и путь к базе
  задаются снаружи, с разумными значениями по умолчанию. Способ развёртывания — голый
  `npx`, контейнер или общий сервис — на код не влияет.

## 7. Ограничения

Осознанно принятые границы этапа 1. Для MVP и MLP истории git достаточно — эти пункты
не блокируют выпуск. Возможно, снимем их позже, но отдельным решением, а не по ходу дела.

- **Ответ ограничен тем, что написано в заголовке MR.** Описания у 62% пустые, кода
  мы не индексируем. Если фичу сделали, но назвали MR «fix», найти её нечем.
- **Индекс устаревает.** Он строится командой и живёт на диске; свежие MR не появятся
  в нём сами, пока индексацию не запустят снова.
- **Индекс MR не попадает в пакет и никуда не публикуется.** В нём 22 365 заголовков
  по проектам заказчиков. В `files` пакета только `dist`; сборка индекса — дело машины
  пользователя.
- **Репозиторий должен быть склонирован локально.** Сервер не ходит в сеть и не клонирует
  сам — работает только с тем, что уже есть на диске.

## 8. Открытые вопросы

- Где живёт индекс: у каждого локально (ollama и 13 минут индексации на своей машине,
  копии расходятся) или один общий сервис внутри периметра компании (ставить нечего,
  но нужен контейнер и его сопровождение).
- Порядок поиска для вопроса «делали мы такое?»: сначала точный по коду через API GitLab,
  потом смысловой по MR — или наоборот. Проверяется только на практике.
